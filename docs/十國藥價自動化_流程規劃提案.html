01

這份提案要解決什麼

原構想的三項自動化需求方向正確，本提案予以保留：依匯入的藥品清單擷取各國健保支付價格、 留存網站頁面截圖作為佐證、以及把所有操作統一在一個 HTML 介面上。

調整的唯一理由

查得的十國藥價將作為藥價調整時的市場交易價資料之一。 錯誤的代價遠高於慢一點。 因此凡是牽涉「判斷」的步驟，設計上一律讓程式收斂選項、由人拍板， 並留下誰在什麼時候做了什麼決定的紀錄。

02

對原流程的五項調整

調整一

程式不「選出價格」，只「收斂候選」，由人拍板

實際的人工流程包含兩個判斷步驟：用商品名加成分名查出同成分清單後， 搭配商品名與藥商名判斷哪一個是原廠藥； 接著在原廠藥的各種規格中，選擇要用哪個劑型、含量、包裝。

這兩步都是判斷，不是查表。錯判原廠藥或選錯可比規格，結果會是一個 「看起來很正常、但其實錯了」的價格——而且一旦寫進藥價調整就很難被發現。

步驟由誰做說明
依成分名撈出同成分全部品項程式機械性比對，程式做得比人準
計算單位藥品價格並排序程式純算術，且保留分子分母供覆核
判定哪一筆是原廠藥人程式只提供線索：商品名相符度、藥商名相符度、原始檔的學名藥註記、收載日期
確認選用的規格可比人程式標示建議值（單位藥價最低者），由人勾選確認
記錄決定者與決定時間程式供未來爭議時回溯

實務上每個藥品多一個確認畫面，成本很低；換到的是每一筆價格都有人負責、有紀錄可查。

調整二

價格必須連同「包裝數量」與「價格類別」一起存

包裝數量已納入。另外要補一個容易出事的欄位：價格類別。 各國公布的並不是同一種價格——

國家常見的兩種價格差別
瑞典AIP 藥局採購價／AUP 藥局零售價AUP 含藥局加成
瑞士FAP 廠商出廠價／PP 藥局零售價PP 含配銷加成與稅
法國Prix Fabricant HT／Prix Public TTC含稅與否、通路加成
德國Festbetrag 固定給付額／Apothekenverkaufspreis 藥局零售價給付上限 vs 實際售價
澳洲多個價格欄位（含 cp2p）是否含調劑費等

把甲國的出廠價和乙國的零售價放進同一欄比較，數字會系統性偏差。因此：

  • 每一筆價格都帶「價格類別」標籤，且在介面上一直顯示，不能只藏在檔案裡
  • 單位藥價排序只在同一價格類別內進行
  • 匯出檔一律分欄呈現，不做跨類別的「代表價」
調整三

截圖升級為「佐證包」

單獨一張 PNG 的證據力其實不強——它沒辦法自己證明是什麼時候、從哪個網址拍的。 既然目的是爭議發生時作為佐證，建議每次擷取產出一組：

內容用途
整頁截圖 PNG主要佐證。全頁而非可視區——價格常在捲軸外，只截可視區會漏
該頁原始 HTML 存檔網站改版後仍可還原當時內容
中繼資料檔完整網址、擷取時間（含時區）、HTTP 狀態碼、頁面標題、視窗尺寸、執行人員、PNG 的 SHA-256
批次清單檔一次作業所有檔案的清單與雜湊值，可驗證事後未被抽換

批次下載的原始檔比照辦理：原封不動保存並計算雜湊。 處理後的結果是二手資料，原始檔才是佐證的根。

人工截圖走同一個登錄介面：同仁貼上網址、選擇截圖檔，工具補上時間戳與雜湊。 人工與自動產出的佐證格式一致，也避免來路不明的截圖混進來。

調整四

先做環境檢測，再決定截圖技術路線

既有程式碼顯示，先前有相當比例的時間耗在 Python、Chrome、ChromeDriver 的安裝與版本對應上。 建議先用一支只做檢查、不安裝任何東西的探針程式把環境條件問清楚。 已隨本提案交付，雙擊 執行環境檢測.bat 即可，約 1 至 3 分鐘。

檢查項目包含 Python 版本與模組完整性、檔案讀寫權限、本機介面連接埠、瀏覽器位置與版本、 十四個官方網站的連線與 SSL 憑證情形，以及最關鍵的一項——無頭截圖是否可用。

為什麼這一項最關鍵

若無頭截圖可用，截圖就能直接呼叫 Windows 內建的 Edge， 不需要安裝 Selenium，也不需要處理 ChromeDriver 版本對應， 同仁端的環境問題會少掉一大半。若不可用，再評估 Selenium 或全面改人工。

調整五

兩軌來源並列，而不是二選一

依指示，健保署官方指定網站優先，查無整批下載時才採用另尋得之來源。 建議在設計上讓兩軌同時存在並各自留痕：

  • A 軌（批次檔來源）　整批下載、機讀、可自動比對
  • B 軌（手冊指定網站）　逐筆查詢頁截圖，符合現行作業規範

兩軌價格並列顯示，不一致時介面主動標示。

附帶好處

這樣做會自動累積「兩邊價格是否一致」的證據， 正是澳洲那種情況所需要的依據——當資料足以證明官方批次檔比查詢頁更完整或更適用時， 就有具體材料可以提報修正指定網站，而不必憑印象主張。

03

系統架構

四層，各層可獨立測試、獨立交付。同仁只會看到最上面那一層。

A 層：統一欄位

沿用既有八支腳本的技術原則——只用 Python 標準函式庫、內建 SSL 憑證修法—— 新增一層統一欄位轉換，讓十國資料進到同一張表。

欄位群內容
來源國家代碼、來源機關、來源軌別（A／B）
佐證資料版本日期、下載時間、來源網址、原始檔雜湊
識別各國原生藥品碼（PZN、CIP、DIN、Varunummer、PBS code、YJ code 等）
比對商品名、成分名（原文）、ATC
規格劑型、含量（數值與單位分開存）、包裝數量（數值與單位）
價格當地價格、幣別、價格類別
判定線索藥商、藥證持有商、學名藥註記
計算單位藥價（價格÷包裝數量，保留分子分母）

不做的事

本工具只存當地幣別的原始價格，不做匯率換算。 換算基準日與匯率來源屬政策決定，需另行規定。

B 層：比對與候選收斂

三段式比對，每筆結果都標示比對依據與信心層級：

層級條件處理
第一級成分名＋ATC＋含量＋劑型 皆命中列為建議候選
第二級成分名命中，含量或劑型待確認列出，標示待確認欄位
第三級僅商品名模糊命中一律標示需人工判讀

比對前先做正規化：大小寫、全半形、鹽類字尾（hydrochloride／HCl／mesylate 等）， 以及各國語言的成分名對照（如 apixaban／Apixaban／アピキサバン）。 對照表隨使用逐步累積，查過的自動記住。

D 層：操作介面

以 Python 標準函式庫的 http.server 在本機開一個網頁介面， 同仁雙擊一個 .bat 就會自動開啟瀏覽器，不需要安裝任何東西，也不需要看到命令列。 介面只在本機執行，不對外開放。共六個頁面：總覽、匯入清單、執行下載、複核、佐證作業、匯出。

介面文字全中文、不出現技術術語；每一則錯誤訊息都要寫清楚「這代表什麼」與「您該怎麼做」。

06

需要決定的事項

以下六項屬政策或管理決定，非技術問題，建議一併提請主管核示。

  1. 兩軌來源並列是否符合作業規範既有報告已列為待確認事項，本次一併處理。
  2. 人工複核的責任歸屬誰有權確認原廠藥判定與規格選用，紀錄保存多久。
  3. 英國 TRUD 帳號需個人帳號與 API 金鑰，由誰申請、金鑰如何保管。
  4. 加拿大薩省是否去函 DPEB詢問 ALLDIN 或 PDCMS 主檔可否申請匯出，既有報告待辦事項。
  5. 佐證包保存位置與保存年限涉及爭議時效，需與檔案管理規定對齊。
  6. 匯率換算基準日與匯率來源本工具不做換算，需另行規定。
07

風險與限制

風險說明因應
網站改版各國官方網址定期失效，屬常態介面提供「連線體檢」按鈕，可隨時全國檢查一輪
德國保密給付價2025 年起部分新藥淨價不再公開，侵蝕德國作為參考國之透明度個別品項標示是否適用，並於報告中揭露
政策性停用官方可能停用既有下載管道，如澳洲舊制每次執行記錄來源網址與格式，變動時可立即察覺
robots.txt 與服務條款加拿大薩省已明確禁止自動化存取該國一律人工，不寫爬蟲
截圖之法律效力佐證包提高證據力，但非公證文書個案如需更強證明力，需另循公證或存證程序
欄位對照可信度瑞士、加拿大等國無官方逐欄位定義文件於資料與匯出檔標示可信度等級，不與有官方文件佐證者等同看待
