# 十國藥價自動化機制 — 流程規劃提案

> 提案日期：2026-08-27
> 用途：回應「建立抓取十國藥價之自動化機制」需求，提出調整後之流程規劃，供討論與主管核定。

---

## 一、這份提案要解決什麼

您提出的三項自動化需求（批次下載與篩選、網頁截圖存證、HTML 操作介面）方向正確，本提案予以保留，
並針對三個會影響「資料能不能拿去核價」的關鍵點提出調整。

調整的理由只有一個：**查得的十國藥價將作為藥價調整之市場交易價資料，錯誤的代價遠高於慢一點。**
因此凡是牽涉「判斷」的步驟，設計上一律讓程式收斂選項、由人拍板，並留下誰在什麼時候做了什麼決定的紀錄。

---

## 二、對原流程的五項調整

### 調整一：程式不「選出價格」，只「收斂候選」，由人拍板

您描述的人工流程其實包含兩個判斷步驟：

1. 用商品名＋成分名查出同成分藥品清單後，**搭配商品名與藥商名判斷哪一個是原廠藥**
2. 在原廠藥的各種規格中，**選擇要用哪個劑型／含量／包裝**（換算為單位藥品價格最低者）

這兩步都是判斷，不是查表。錯判原廠藥或選錯可比規格，結果會是一個「看起來很正常、但其實錯了」的價格，
而且一旦寫進藥價調整就很難被發現。

因此建議：

| 步驟 | 由誰做 | 說明 |
|---|---|---|
| 依成分名撈出同成分全部品項 | 程式 | 機械性比對，程式做得比人準 |
| 計算每個品項的單位藥品價格並排序 | 程式 | 純算術，且會保留分子分母供覆核 |
| **判定哪一筆是原廠藥** | **人** | 程式只提供線索：商品名相符度、藥商名相符度、原始檔的學名藥註記、收載日期 |
| **確認選用的規格可比** | **人** | 程式標示建議值（單位藥價最低者），由人勾選確認 |
| 記錄決定者與決定時間 | 程式 | 供未來爭議時回溯 |

實務上每個藥品多一個確認畫面，成本很低；換到的是每一筆價格都有人負責、有紀錄可查。

### 調整二：價格必須連同「包裝數量」與「價格類別」一起存，且不同類別不可互比

您已指出必須儲存包裝數量，這點納入。另外要補一個容易出事的欄位：**價格類別**。

各國公布的不是同一種價格：

| 國家 | 常見的兩種價格 | 差別 |
|---|---|---|
| 瑞典 | AIP（藥局採購價）／AUP（藥局零售價） | AUP 含藥局加成 |
| 瑞士 | FAP（廠商出廠價）／PP（藥局零售價） | PP 含配銷加成與稅 |
| 法國 | Prix Fabricant HT（未稅出廠價）／Prix Public TTC（含稅零售價） | 含稅與否、通路加成 |
| 德國 | Festbetrag（固定給付額）／Apothekenverkaufspreis（藥局零售價） | 給付上限 vs 實際售價 |
| 澳洲 | 多個價格欄位（含您提到的 cp2p） | 是否含調劑費等 |

若把甲國的出廠價和乙國的零售價放在同一欄比較，數字會系統性偏差。因此：

- 每一筆價格都必須帶「價格類別」標籤，且此標籤在介面上一直顯示，不能只藏在檔案裡
- 單位藥價排序**只在同一價格類別內**進行
- 匯出檔一律分欄呈現，不做跨類別的「代表價」

### 調整三：截圖升級為「佐證包」

單獨一張 PNG 的證據力其實不強——它沒辦法自己證明是什麼時候、從哪個網址拍的。
既然目的是「未來爭議發生時作為佐證資料」，建議每次擷取產出一組：

| 內容 | 用途 |
|---|---|
| 整頁截圖 PNG（全頁，非可視區） | 主要佐證；價格常在捲軸外，只截可視區會漏 |
| 該頁原始 HTML 存檔 | 網站改版後仍可還原當時內容 |
| 中繼資料檔（同名 .json） | 完整網址、擷取時間（含時區）、HTTP 狀態碼、頁面標題、視窗尺寸、執行人員、PNG 的 SHA-256 |
| 該批次的清單檔 manifest | 一次作業所有檔案的清單與雜湊值，可驗證事後未被抽換 |

**批次下載的原始檔也比照辦理**：原始檔原封不動保存並計算雜湊，不可只留處理後的結果。
處理後的結果是二手資料，原始檔才是佐證的根。

**人工截圖走同一個登錄介面**：同仁在介面上貼上網址、選擇截圖檔，工具補上時間戳與雜湊，
讓人工與自動產出的佐證格式一致，也避免來路不明的截圖混進來。

### 調整四：先做環境檢測，再決定截圖技術路線

本專案既有程式碼顯示，先前有相當比例的時間耗在 Python／Chrome／ChromeDriver 的安裝與版本對應上。
建議先用一支只做檢查、不安裝任何東西的探針程式，把環境條件一次問清楚，再決定技術路線。

已隨本提案交付：`tools/env_check.py` 與 `執行環境檢測.bat`（雙擊執行，約 1 至 3 分鐘）。

檢查項目：Python 版本與模組完整性、檔案讀寫權限、本機介面連接埠、瀏覽器安裝位置與版本、
**無頭截圖是否可用**、十四個官方網站的連線與 SSL 憑證驗證情形。

其中最關鍵的是無頭截圖測試。若可用，截圖就能直接呼叫 Windows 內建的 Edge，
**不需要安裝 Selenium，也不需要處理 ChromeDriver 版本對應**，同仁端的環境問題會少掉一大半。
若不可用，再評估 Selenium 或全面改人工。

### 調整五：兩軌來源並列，而不是二選一

依您的指示，健保署官方指定網站優先，查無整批下載時才採用另尋得之來源。
建議在設計上讓兩軌**同時存在並各自留痕**，而非擇一：

- **A 軌（批次檔來源）**：整批下載、機讀、可自動比對
- **B 軌（手冊指定網站）**：逐筆查詢頁截圖，符合現行作業規範

兩軌的價格並列顯示，不一致時介面主動標示。這樣做的附帶好處是：
**它會自動累積「兩邊價格是否一致」的證據**，正是您提到澳洲那種情況所需要的依據——
當資料足以證明官方批次檔比查詢頁更完整或更適用時，就有具體材料可以提報修正指定網站，
而不必憑印象主張。

## 三、系統架構

四層，各層可獨立測試、獨立交付。

```
┌─ D 層　操作介面（HTML，本機網頁）────────────────────────┐
│   匯入清單 → 選國家 → 執行 → 複核 → 匯出               │
│   同仁只會看到這一層                                     │
└──────────────────────────────────────────────────────────┘
        │                │                │
┌───────▼──────┐ ┌───────▼──────┐ ┌───────▼──────┐
│ A 層 資料     │ │ B 層 比對     │ │ C 層 佐證     │
│ 批次下載      │ │ 成分名比對    │ │ 自動截圖      │
│ 格式解析      │ │ 候選收斂      │ │ 人工截圖登錄  │
│ 原始檔留存    │ │ 單位藥價計算  │ │ 中繼資料      │
│ 統一欄位轉換  │ │ 人工複核紀錄  │ │ 雜湊與清單    │
└──────────────┘ └──────────────┘ └──────────────┘
```

### A 層：批次下載與統一欄位

沿用既有八支腳本的技術原則（只用 Python 標準函式庫、內建 SSL 憑證修法），
新增一層統一欄位轉換，讓十國資料進到同一張表：

| 欄位 | 說明 |
|---|---|
| 國家代碼／來源機關／來源軌別 | A 軌或 B 軌 |
| 資料版本日期／下載時間／來源網址／原始檔雜湊 | 佐證用 |
| 各國原生藥品碼 | PZN、CIP、DIN、Varunummer、PBS code、YJ code 等 |
| 商品名／成分名（原文）／ATC | 比對用 |
| 劑型／含量（數值＋單位分開存）／**包裝數量（數值＋單位）** | 規格 |
| **當地價格／幣別／價格類別** | 核心資料 |
| 藥商／藥證持有商／學名藥註記 | 原廠判定線索 |
| 單位藥價（＝價格÷包裝數量，並保留分子分母） | 程式計算 |

**本工具只存當地幣別的原始價格，不做匯率換算。** 換算基準日與匯率來源屬政策決定，需另行規定。

### B 層：比對與候選收斂

三段式比對，每筆結果都標示比對依據與信心層級：

| 層級 | 條件 | 處理 |
|---|---|---|
| 第一級 | 成分名＋ATC＋含量＋劑型 皆命中 | 列為建議候選 |
| 第二級 | 成分名命中，含量或劑型待確認 | 列出，標示待確認欄位 |
| 第三級 | 僅商品名模糊命中 | 一律標示需人工判讀 |

比對前先做正規化：大小寫、全半形、鹽類字尾（hydrochloride／HCl／mesylate 等）、
以及各國語言的成分名對照（如 apixaban／Apixaban／アピキサバン）。
成分名對照表可隨使用逐步累積，查過的自動記住。

### C 層：佐證擷取

依調整三辦理。自動與人工兩種來源，產出格式一致。

檔名規範：`{國別}_{擷取日期}_{藥品識別}_{來源軌別}_{序號}.png`

### D 層：HTML 操作介面

以 Python 標準函式庫的 `http.server` 在本機開一個網頁介面，
同仁雙擊一個 .bat 就會自動開啟瀏覽器，**不需要安裝任何東西，也不需要看到命令列**。
介面只在本機執行，不對外開放。

六個頁面：

1. **總覽**　各國資料版本日期、上次下載時間、狀態燈號
2. **匯入藥品清單**　拖放或貼上，欄位對應精靈（商品名、成分名、ATC、含量劑型、藥商）
3. **執行下載**　勾選國家、進度顯示、即時訊息
4. **複核**　候選清單、原廠勾選、單位藥價排序、兩軌價格並列比對
5. **佐證作業**　自動截圖執行、人工截圖登錄
6. **匯出**　資料檔、佐證包、作業紀錄

介面文字全中文、不出現技術術語；每一則錯誤訊息都要寫清楚「這代表什麼」與「您該怎麼做」。

## 五、分階段時程

刻意把「操作介面」排在「比對層」之前，讓同仁能先用起來，邊用邊回饋。

| 階段 | 內容 | 產出 |
|---|---|---|
| **0**（本次已交付） | 環境檢測探針 | 檢測報告，據以定案截圖技術路線 |
| **1** | 統一欄位層＋接上五個已完成國家（日、法 CIP、比、瑞典、澳）＋原始檔留存與雜湊 | 五國資料可進同一張表 |
| **2** | HTML 操作介面骨架（匯入、選國家、執行、看進度、匯出） | **同仁可實際上手使用** |
| **3** | 比對層＋複核畫面（成分名對照、候選清單、單位藥價、人工勾選） | 完整比對流程 |
| **4** | 佐證包（自動截圖＋人工登錄，兩軌並行） | 可供爭議舉證之佐證包 |
| **5** | 補齊剩餘國家：瑞士欄位驗證、英國 TRUD、法國 UCD、德國、加拿大 PDF | 十國到位 |

各階段結束都交付可執行的成果，不會出現「全部做完才看得到東西」的情況。

## 六、需要決定的事項

以下六項屬政策或管理決定，非技術問題，建議一併提請主管核示：

1. **兩軌來源並列是否符合作業規範**（既有報告已列為待確認事項，本次一併處理）
2. **人工複核的責任歸屬**：誰有權確認原廠藥判定與規格選用，紀錄保存多久
3. **英國 TRUD 帳號**：需個人帳號與 API 金鑰，由誰申請、金鑰如何保管
4. **加拿大薩省是否去函 DPEB** 詢問 ALLDIN／PDCMS 主檔可否申請（既有報告待辦事項）
5. **佐證包保存位置與保存年限**：涉及爭議時效，需與檔案管理規定對齊
6. **匯率換算基準日與匯率來源**：本工具不做換算，需另行規定

## 七、風險與限制

| 風險 | 說明 | 因應 |
|---|---|---|
| 各國網站改版導致程式失效 | 官方網址定期失效，屬常態 | 介面提供「連線體檢」按鈕，可隨時全國檢查一輪 |
| 德國保密給付價 | 2025 年起部分新藥淨價不再公開，侵蝕德國作為參考國之透明度 | 個別品項標示是否適用，並於報告中揭露 |
| 政策性停用（如澳洲舊制） | 官方可能停用既有下載管道 | 每次執行記錄來源網址與格式，變動時可立即察覺 |
| robots.txt 與服務條款 | 加拿大薩省已明確禁止自動化存取 | 該國一律人工，不寫爬蟲 |
| 截圖之法律效力 | 佐證包提高證據力，但非公證文書 | 如個案需更強證明力，需另循公證或存證程序 |
| 欄位對照未經官方文件驗證 | 瑞士、加拿大等國無官方逐欄位定義文件 | 於資料與匯出檔標示可信度等級，不與有官方文件佐證者等同看待 |
